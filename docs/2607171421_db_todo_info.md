## що додаємо
```text
Таблиці
groups
	id
    "name"
    descr
    is_active
    date/user
user_groups
    user_id
    group_id
    descr
    date/user
    composite PK (user_id, group_id)
section_group_access
    section_id       -- який розділ
    group_id         -- яка група
    access_level     -- 'view' | 'edit'
    is_inherited       -- bool: чи це успадковане значення
    date/user
    PRIMARY KEY (section_id, group_id)

Ролі можуть будуть наступні :
    - admin - повний доступ
    - editor - доступ на редагування іконок, шаблонів, розділів
    - user - перегляд іконок та шаблонів (можливо інших налаштувань), та робота з Розділами і їх змістом
    - viewer - тільки перегляд розділів

Привілеї для ролей будуть наступні :
    - admin - редагування користувачів, ролей, привілеїв та глобальних налаштувань якихось в майбутньому.
    - admin-view - перегляд користувачів, ролей, привілеїв та глобальних налаштувань якихось в майбутньому.
    - icons-edit - редагування іконок
    - icons-view - перегляд іконок
    - logs-view
    - sections-full - повний доступ до всіх розділів
    - sections-edit
    - sections-view
    - section_categories-edit
    - section_categories-view
    - section_document_info_block_styles-edit
    - section_document_info_block_styles-view
    - templates-edit
    - templates-view

Групи для початку можуть бути такі :
    - Адміністратори
    - Розробники
    - Тестери
    - Супровід
    - Менеджери
    - Бухгалтери

Ролі вказують куди і який буде доступ. Наприклад доступ до іконок тільки на перегляд.
Групи вказують саме до яких елентів є доступ. Наприклад у конкретної групи є доступ до розділу "Документація для розробників" на читання, 
а другої групи на цей розділ є права на редагування.

Коли юзер створює Розділ другого рівня (від загального кореня) він вказує які Групи до яких він входить мають сюди дуступ і який.
При створені підрозділів цього розділу вони успадковують налаштування доступу свого предка і можуть змінюватись тільки в сторону зменшення доступу.
```

## 🔧 Рекомендації

### Структура для розділів з успадкуванням

```sql
sections
    id
    parent_id          -- NULL для кореня
    name
    inherit_access     -- bool: чи успадковувати від предка
    created_by / at

section_group_access
    section_id
    group_id
    access_level       -- ENUM: 'view', 'edit', 'full'
    is_inherited       -- bool: чи це успадковане значення
    granted_by
    granted_at
    PRIMARY KEY (section_id, group_id)
```

Логіка перевірки при запиті доступу:
```
1. Знайти групи користувача
2. Знайти access_level для section + group
3. Якщо немає — піднятись по parent_id (рекурсія / CTE)
4. Порівняти з максимальним рівнем ролі користувача
5. Взяти мінімум
```

### Використовуй `ltree` або `path` для ієрархії розділів

PostgreSQL має розширення `ltree` яке ідеально підходить для дерев з успадкуванням:
```sql
section_path ltree  -- '1.5.23' — шлях в дереві
```
Це дозволить знайти всіх предків одним запитом замість рекурсивного CTE.
