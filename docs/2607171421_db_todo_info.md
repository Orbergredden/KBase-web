#### 4. **`date_modified_info` в `sections` — можлива денормалізація**
Оновлюється тригером з `section_document_info_block_headers` + `section_dictionaries`.
**Ризик:** Рас-умови (race conditions) при паралельних оновленнях.
**Рекомендація:** 
- Або зробити `date_modified_info` **MATERIALIZED VIEW** / функція `get_section_last_modified(section_id)`
- Або тригер обгорнути в `FOR SHARE` / advisory lock
- Або прийняти eventual consistency (для MVP — ок).

### 7. `show_level` — вузьке рішення для прав доступу

Поле `show_level int` (0=приватний, 1=зареєстровані, 2=публічний) є простим, але не масштабованим. У проекті вже є таблиці `roles` і `privileges`.

**Рекомендація:** Розглянути зв'язок між `sections` та `roles`:
```sql
kbase.section_access  -- таблиця прав доступу до розділів
    section_id bigint,
    role_id bigint,
    access_level smallint  -- 1=read, 2=write, 3=delete
```
Або залишити `show_level` як "базовий рівень" і додати більш гранульовані права пізніше — це також прийнятне рішення для MVP.

### Немотрон
#### 3. **`show_level` в `sections` — обмежений контроль доступу** (згідно ваших нотаток)
Поточне: `int DEFAULT 0` (0=private, 1=registered, 2=public).
**Рекомендація:** Залишити як "базовий рівень" для MVP, але підготувати грунт для `section_access`:
```sql
-- Майбутня таблиця (поки не створювати, але мати в плані)
CREATE TABLE kbase.section_access (
    section_id BIGINT REFERENCES kbase.sections(id) ON DELETE CASCADE,
    role_id    BIGINT REFERENCES kbase.roles(id) ON DELETE CASCADE,
    access_level SMALLINT NOT NULL CHECK (access_level IN (1,2,3)), -- 1=read, 2=write, 3=admin
    PRIMARY KEY (section_id, role_id)
);
```
Логіка: `show_level` = fallback, `section_access` = granular override.
