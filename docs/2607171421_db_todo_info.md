## ⚠️ Зауваження

### 1. Схема `user_groups` — надлишкова колонка `id`
`user_groups` — це таблиця зв'язків (junction table). `id` тут зайвий, достатньо composite PK `(user_id, group_id)`.

### 2. Немає зв'язку груп з доступом до розділів
Ти описав це словами, але в схемі немає таблиці яка пов'язує **групу + розділ + рівень доступу**. Без неї реалізувати фічу неможливо.

Потрібна таблиця типу:
```sql
section_group_access
    section_id       -- який розділ
    group_id         -- яка група
    access_level     -- 'view' | 'edit' | 'full'
    granted_by       -- user_id хто дав доступ
    granted_at       -- timestamp
```
## 🔧 Рекомендації

### Структура для розділів з успадкуванням

```sql
sections
    id
    parent_id          -- NULL для кореня
    name
    inherit_access     -- bool: чи успадковувати від предка
    created_by / at

section_group_access
    section_id
    group_id
    access_level       -- ENUM: 'view', 'edit', 'full'
    is_inherited       -- bool: чи це успадковане значення
    granted_by
    granted_at
    PRIMARY KEY (section_id, group_id)
```

Логіка перевірки при запиті доступу:
```
1. Знайти групи користувача
2. Знайти access_level для section + group
3. Якщо немає — піднятись по parent_id (рекурсія / CTE)
4. Порівняти з максимальним рівнем ролі користувача
5. Взяти мінімум
```

### Використовуй `ltree` або `path` для ієрархії розділів

PostgreSQL має розширення `ltree` яке ідеально підходить для дерев з успадкуванням:
```sql
section_path ltree  -- '1.5.23' — шлях в дереві
```
Це дозволить знайти всіх предків одним запитом замість рекурсивного CTE.

### Enum для `access_level`
```sql
CREATE TYPE access_level AS ENUM ('view', 'edit', 'full', 'none');
```

### 🏗️ Рекомендована схема БД (розширена)

```sql
-- 1. Групи (контейнери доступу до об'єктів)
CREATE TABLE groups (
    id BIGSERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL UNIQUE,
    description TEXT,
    is_active BOOLEAN DEFAULT true,
    created_at TIMESTAMPTZ DEFAULT now(),
    updated_at TIMESTAMPTZ DEFAULT now(),
    created_by BIGINT REFERENCES users(id),
    updated_by BIGINT REFERENCES users(id)
);

-- 2. Користувач ↔ Група (many-to-many)
CREATE TABLE user_groups (
    user_id BIGINT REFERENCES users(id) ON DELETE CASCADE,
    group_id BIGINT REFERENCES groups(id) ON DELETE CASCADE,
    description TEXT,
    created_at TIMESTAMPTZ DEFAULT now(),
    created_by BIGINT REFERENCES users(id),
    PRIMARY KEY (user_id, group_id)
);

-- 3. Група ↔ Роль (які ролі має група) — ОПЦІОНАЛЬНО, але рекомендовано
CREATE TABLE group_roles (
    group_id BIGINT REFERENCES groups(id) ON DELETE CASCADE,
    role_id BIGINT REFERENCES roles(id) ON DELETE CASCADE,
    PRIMARY KEY (group_id, role_id)
);

-- 4. Доступ груп до розділів (ABAC: група + розділ + рівень)
CREATE TABLE section_group_access (
    section_id BIGINT REFERENCES sections(id) ON DELETE CASCADE,
    group_id BIGINT REFERENCES groups(id) ON DELETE CASCADE,
    access_level SMALLINT NOT NULL CHECK (access_level IN (1,2,3)), -- 1=read, 2=write, 3=admin
    created_at TIMESTAMPTZ DEFAULT now(),
    created_by BIGINT REFERENCES users(id),
    PRIMARY KEY (section_id, group_id)
);

-- 5. (Опціонально) Роль ↔ Розділ — для глобальних прав ролей на розділи
CREATE TABLE section_role_access (
    section_id BIGINT REFERENCES sections(id) ON DELETE CASCADE,
    role_id BIGINT REFERENCES roles(id) ON DELETE CASCADE,
    access_level SMALLINT NOT NULL CHECK (access_level IN (1,2,3)),
    PRIMARY KEY (section_id, role_id)
);

-- 6. Спрощені привілеї (ресурс + дія)
-- Замість icons-edit, icons-view, sections-edit...
-- робимо: resource + action
CREATE TABLE privileges (
    id BIGSERIAL PRIMARY KEY,
    resource VARCHAR(50) NOT NULL,  -- 'icons', 'sections', 'templates', 'categories', 'styles', 'users', 'roles', 'settings', 'logs'
    action VARCHAR(20) NOT NULL,    -- 'read', 'write', 'delete', 'admin'
    description TEXT,
    UNIQUE (resource, action)
);
-- Приклади: ('icons','read'), ('icons','write'), ('sections','read'), ('sections','write'), ('sections','delete'), ('sections','admin')
```

### 🔐 Логіка перевірки доступу (псевдокод)

```java
boolean hasAccess(User user, Section section, String resource, String action) {
    // 1. Адмін — повний доступ
    if (user.hasRole("ROLE_ADMIN")) return true;

    // 2. Перевірка глобальних привілеїв ролей користувача
    if (user.hasPrivilege(resource, action)) return true;

    // 3. Перевірка section_role_access (роль має доступ до цього розділу)
    if (sectionRoleAccessExists(section.id, user.roleId, action)) return true;

    // 4. Перевірка section_group_access (групи користувача мають доступ)
    Set<Long> userGroupIds = user.getGroupIds();
    if (sectionGroupAccessExists(section.id, userGroupIds, action)) return true;

    // 5. Спадкування: перевіряємо батьківські розділи (рекурсивно вгору)
    Section parent = section.getParent();
    while (parent != null) {
        if (sectionGroupAccessExists(parent.id, userGroupIds, action)) return true;
        if (sectionRoleAccessExists(parent.id, user.roleId, action)) return true;
        parent = parent.getParent();
    }

    return false;
}
```

### ❓ Питання для уточнення

1. **Чи потрібна many-to-many ролей для користувача?** (зараз `role_id` — single)
2. **Чи будуть групи створюватися адмінами, чи користувачі можуть створювати власні групи?**
3. **Як обробляти конфлікт:** група дає `write`, а батьківський розділ — тільки `read`? (ваше правило "тільки зменшення" вирішує це, але треба ефорсити)
4. **Чи потрібні тимчасові права / термінові дії?** (наприклад, доступ на 1 день)
5. **Фронтенд:** чи потрібно передавати в JWT/токен всі ефективні права, чи робити перевірку на бекенді при кожному запиті?

## Оцінка

Загалом, логіка **Roles = Capabilities** (що можна робити з типом ресурсу), **Groups = Resource-level access** (до яких конкретно ресурсів) — це правильний підхід. Але є кілька проблем.

---

### 1. Немає таблиці, яка зв'язує Groups з розділами

Це головна прогалина. Ви описуєте: "група має доступ до розділу 'Документація' на читання", але в схемі немає де це зберігати.

**Потрібно додати:**

```text
section_group_permissions
    id
    section_id       -> sections.id
    group_id         -> groups.id
    privilege_id     -> privileges.id  (або рівень: view/edit/full)
    is_inherited     boolean          (чи успадковано від предка)
    created_at
    created_by
```

А також саму таблицю `sections` з підтримкою ієрархії:

```text
sections
    id
    parent_id        -> sections.id (nullable для кореневих)
    name
    ... (інші поля)
    created_at
    updated_at
```

---

### 2. Inheritance "тільки в сторону зменшення" — потребує механіки

Ваше правило: дочірній розділ успадковує доступ від предка і може тільки **обмежувати** (не розширювати). Це добре, але:

- При створенні підрозділу потрібно копіювати permissions від батька з `is_inherited = true`
- При зміні — можна або залишити (`is_inherited = true`), або перевизначити з суворішим privilege
- При перевірці доступу: юзер має доступ до розділу, якщо хоч одна з його груп має достатній рівень **на цей конкретний розділ** (або предок з успадкуванням)

Реалізувати можна через рекурсивний CTE або через **closure table** для sections.

---

### 3. Одна роль на юзера — обмеження

Зараз `users.role_id` — це **одна** роль. Якщо юзер має бути і `editor`, і мати `admin-view` на користувачів — доведеться створювати гібридну роль. 

**Рекомендація:** зробити `user_roles`:
```text
user_roles
    user_id
    role_id
```

Хоча якщо ролі взаємовиключні — залиште як є.

---

### 4. Привілеї занадто плоскі

`icons-edit`, `sections-full`, `section_categories-view` — це все в одній таблиці `privileges`. Немає групування.

**Рекомендація:** додати `module` або префікс як окреме поле:
```text
privileges
    id
    name           (наприклад "edit")
    module         (наприклад "icons", "sections", "admin")
    description
```

Тоді перевірка буде: `has_privilege(user_id, 'sections', 'edit')`.

---

### 5. Поле `"password"` в лапках — червоний прапорець

Сподіваюсь, це просто коментар в діаграмі, а не реальне зберігання в plain text. Має бути хеш (bcrypt/argon2). Якщо лапки через те, що це ключове слово SQL — ок.

---

### 6. Аудиторські поля (`date/user`) — невизначені

Розбийте на:
```text
created_at    timestamp
created_by    integer -> users.id
updated_at    timestamp (nullable)
updated_by    integer -> users.id (nullable)
```

Або шарова таблиця `audit_log`.

---

### 7. Групи: `is_active` — добре, але не вистачає `is_system`

Для вбудованих груп (Розробники, Тестери тощо) варто додати `is_system boolean`, щоб випадково не видалили.

---

### 8. Як Groups пов'язані з іншими ресурсами, крім розділів?

Ви пишете "до яких **елементів** є доступ". Якщо Groups будуть використовуватись не тільки для Sections, варто зробити поліморфну таблицю:

```text
group_resource_permissions
    group_id
    resource_type    ('section', 'icon', 'template', ...)
    resource_id
    privilege_id
```

Але для початку можна тільки `section_group_permissions`, а потім розширити.
